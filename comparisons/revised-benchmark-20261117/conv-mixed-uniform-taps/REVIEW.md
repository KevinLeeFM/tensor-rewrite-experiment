# Independent review: mixed U32 convolution with uniform taps

**Verdict: accepted as a counterexample to all six frozen mixed-type/reversal universal claims in the stated evaluator-shaped model.** A single valid output whose `n=66052` terms are all `255×255` distinguishes a U64 convolution sum clamped once to U32 from the emitted U32 multiply/reduce result. The witness works for U8/U8, U8/U32, and U32/U8 parameters, with reversal either enabled or disabled. This is a bounded mixed-width numerical outcome, not a general arbitrary-data equivalence proof, native execution, or C++–Lean correspondence result.

## Source calculation and reduction behavior

I inspected `FREEZE.md`, all three Lean files, replay/hash manifests, and the pinned source code in `algebraic_simplifier.cc`, `hlo_evaluator.cc`, and `hlo_evaluator_typed_visitor.h`. At `SimplifyConvToMultiply` (`algebraic_simplifier.cc:11123–11147`), the spatial guard accepts a nonunit kernel extent when the output spatial extent is one; unit stride/padding/dilation and one input feature per feature group are also required. For `n=66052`, choose rank-three shapes `lhs=[1,n,2]`, `kernel=[n,1,2]`, and output `[1,1,2]` in standard batch/spatial/feature numbering, with `feature_group_count=2`, `batch_group_count=1`, and window extent `n`, stride one, no padding/dilation. This is nonempty and valid; each of the two feature groups selects one input and one kernel-output channel. The packet's uniform value on every spatial tap is 255.

For nonunit kernel spatial extent, the simplifier adds the output spatial axis to `reduction_dimensions`; when `window_reversal` is set, it also adds the corresponding kernel axis to the reversal list (`:11164–11178`). It converts differing operands to the result type, multiplies the broadcast operands, then reduces with an initial zero converted to the result type and an Add reducer (`:11181–11216`). In this U32-result model, each emitted product is 65025, which is exactly representable in U32. Reversal merely permutes equal terms, so the frozen uniform-tap witness has the same list of products with either reversal flag.

The original evaluator converts operands to the declared U32 result type (`hlo_evaluator.cc:6558–6569`), selects U64 for unsigned elementwise arithmetic (`:5767–5778`), and widens values for its convolution loop. It accumulates each tap product into a U64 `result_val` (`:5986`, `:5993–6038`, `:6040–6065`) and clamps the completed sum once to the U32 result bounds (`:5926–5944`, `:6080–6085`) before storing U32 (`:6656–6670`). With the frozen values, each term is 65025 and the total `66052×65025 = 4,295,031,300` is far below U64 maximum, then saturates to `4,294,967,295`.

For the emitted graph, the reduction accumulator and reducer operands have U32 shape. `HloEvaluator::HandleReduce` iterates the reduced indices through `PerformReductionStep`, which copies the current U32 accumulator and current U32 input term into the reducer computation and writes the U32 reducer result back after each step (`hlo_evaluator.cc:4706–4757`, `:4760–4784`, `:4821–4829`, `:4833–4851`). Its fast-add path is restricted to floating-point reductions (`:4771–4773`), so it does not bypass these U32 steps. The typed U32 Add performs its internal unsigned widened operation and narrows to `ReturnT` after each scalar result (`hlo_evaluator_typed_visitor.h:518–524`, `:1194–1218`); thus the reducer implements addition modulo 2^32 at each step. The U32 multiply visitor also narrows its U64 elementwise product back to U32 (`:484–490`, `:1194–1218`); here 65025 already fits, so per-product narrowing changes nothing. Reordering equal terms cannot change the modular sum.

## Formal claim, witness, and overlap

`FoldSpec.Claim` quantifies every `n>1` and all values of the chosen U8/U32 parameter pair for a scalar output fold. `refuted` proves this universal claim false for every pair of storage kinds and both reversal flags. At `n=66052`, byte and word values are all set to 255. The original is `U32_MAX`; the replacement is `4,295,031,300 mod 2^32 = 64,004`. Since the source shapes have two feature groups and the same per-group scalar formula, one such output is enough to refute equality of the full output tensors. The local proof intentionally keeps the common reduction scalar rather than allocating or materializing 66,052-entry arrays.

`FoldControls` checks the concrete saturated and wrapped outputs, and a predecessor length: `n=66051` gives `4,294,966,275`, which is 1,020 below U32 maximum, so both folds agree there. The symbolic `repeatSum` proof justifies these closed values for arbitrary list length and does not rely on a large list evaluation. For `a,b ∈ {byte,word}` it also covers U32/U32, though that pair is outside the six mixed-cast labels listed in the freeze.

This is new relative to `conv-mixed-u32`: that earlier packet handles one pointwise tap, where U8/U8 products are at most 65025 and the U32 clamp is inert; its single-cast counterexamples concern operand magnitudes and not a many-term reduction. It also differs from `conv-full-taps`, which proves the arbitrary physical-axis contraction/reversal/reshape case over exact Nat and same-type arithmetic, not finite-width U32 multiplication/reduction versus U64 accumulation/clamping. The common witness refutes the six IDs `reduce-001`, `reduce-010`, `reduce-011`, `reduce-101`, `reduce-110`, and `reduce-111`; it is one mathematical counterexample pattern, not six independent discoveries. The packet does not prove all nonuniform arrays or close the broader convolution source family.

The proof abstracts a single valid output fold rather than embedding its feature-group tensors, shape inference, and layout transport into Lean. The stated group-count-two source construction supplies the witness's interpretation; previous `conv-full-taps` work supplies related physical contraction reasoning for the exact-Nat case, but is not an imported dependency here. Accordingly, this review accepts the counterexample as sufficient for disproof of universal equality under the stated source-shaped profile, not as a complete full-tensor correspondence theorem. No claim is made about a particular optimizer pipeline reaching this branch or a native backend's execution.
