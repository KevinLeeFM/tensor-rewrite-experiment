On that domain these factors commute and 0.5 is exactly one half. The source-ordered statement needs a pointwise mul_comm adapter to the archived conclusion. To preserve the same literal-order receipt convention as numerical-reuse-review.md, no separately checked row is added for that adapter. No result here for negative reals, principal complex log, or rounded operands.
* **Maximum through erf, logistic and tanh.** Lines 4908–4917 whitelist the opcode; 5018–5026 check both opcodes are identical and apply that op to the maximum of their inputs. Earlier same-instruction and other maximum folds can return first. The branch has no guard equating the two input precisions. For a single exact real function f the missing evidence is function-specific monotonicity on the declared domain, followed by max(f(x),f(y)) = f(max(x,y)). The source opcode list and its SMT comment assume this property; neither establishes it for these three functions. A search of repository Lean declarations and historical receipts yielded no terminal instance for any of them. An exact real result would also leave mixed element precision unresolved. The existing maximum.cbrt-mixed-precision row refutes a particular correctly rounded mixed-grid cube-root model. Its strict cubed-midpoint controls certify only cube root, so it supplies no witness for these three named functions.
