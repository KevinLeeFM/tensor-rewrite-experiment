# Slice-shape separation compatibility assessment

**Result: the isolated split is mechanically viable for its selected examples but is not compatible with the existing transitive public-import API. It must not be integrated as tested.** The sources, frozen manifests and previous worktrees remain unchanged. The copied prototype and repeatable tests are retained to make the obstacle concrete.

## Actual dependencies

`TensorRewrite/Pilot/SliceShape.lean` defines the axis/count/well-formedness core and the two source-shaped transforms `removeRedundantStride` and `reorderReverse`. A `git grep` over tracked Lean sources finds direct uses of those transform names only in `Pilot/EmptySliceRefutation.lean` and the `tests/fixtures/EmptySliceControls.lean` / `InvalidEmptySlice.lean` fixtures, aside from their definitions. The refutation imports `SliceShape` directly; the fixtures import the `TensorRewrite` root, which imports that refutation. `comparisons/tensorright-v1/ReverseSliceFailure.lean` directly imports `SliceShape` for its own paper-specific axis/well-formedness witness. `Pilot/SliceIndexBounds.lean` directly imports `SliceShape` for `IsWellFormed` and `coordinate_bounds`, and `Pilot/IndexMaps.lean` directly imports those bounds. Many maintained and paper modules import `IndexMaps` and use its core axis/index model; prior import inventory records their names. An import is not necessarily a use of every declaration. External clients and dynamic or generated uses are not exhaustively known.

`comparisons/tensorright-v1/dependency-costs.json` and the earlier held-out/library inventories record hashes of `SliceShape.lean` and `SliceIndexBounds.lean`. A live source edit would therefore change historical bytes and cannot be called a replay of the frozen checkpoint. Archived revisions/worktrees must remain independently usable.

## Prototype and results

The four copied files under `prototype/TensorRewrite/Pilot/` put exact original axis/count/well-formedness declarations into `SliceShapeCore`, the exact two transform declarations into `SliceShapeTransforms`, and make the legacy `SliceShape` import the transforms. A copied `SliceIndexBounds` instead imports core. Only the copied tree was changed; originals have their prior hashes. The runner compares declaration text, builds fresh original and prototype graphs with Lean 4.35.0, checks identical `#print` declaration output and axiom audits, compiles actual `EmptySliceRefutation` and paper `ReverseSliceFailure`, and checks nonempty transform examples. The coordinator targeted replay passed in 6.577 seconds (20 Lean subprocesses); the fresh independent replay passed in 7.219 seconds. Two failed harness attempts and their repair are retained in `failures.md`. Neither replay builds all downstream consumers or claims source/Lean correspondence.

The test importing `IndexMaps` alone demonstrates the critical tradeoff: in the original graph `removeRedundantStride` is visible through the public chain `IndexMaps → SliceIndexBounds → SliceShape`; in the prototype it is rejected as an unknown identifier. This demonstrates successful isolation **and** a breaking transitive API change. The runner's `passed` result means that the expected difference was detected; it does not satisfy the user's compatibility requirement. The independent reviewer returned **revise** for migration acceptance; see `independent-review.md`. Both original source definitions and old direct `SliceShape` facade behavior matched in the tested graph.

## Safe next design, not implemented

A compatibility-preserving direction would retain the existing legacy import surfaces and offer a separately named core-only dependency path, then migrate willing internal callers in an explicitly scoped change. This needs a design that avoids duplicate declarations when legacy and core paths are imported together, preserves Lean names and public visibility, accounts for all affected importers and frozen manifests, and tests old and new consumers together. Keeping `SliceIndexBounds` on the legacy facade alone would preserve its transitive API but also keep transforms in the `IndexMaps` closure; achieving both goals can therefore require additional module layering. No such migration has been proved or attempted here. If preserving old byte-level replay in the same checkout is required, frozen files must remain untouched and historical results must be replayed from their pinned revision or separately maintained snapshot.
